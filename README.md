# ПравСтратег — сайт юридической компании

Сайт юридической компании «ПравСтратег» под руководством Ивана Новикова.
Домен — `pravstrateg.ru`. Исполнитель услуг: ИП Новиков Иван Владимирович,
Калининградская область.

## Зачем нужен сайт

Компания оказывает юридические услуги частным клиентам и бизнесу. Задача
сайта — не витрина с прайсом, а первичный отбор и приём обращений: человек
с правовой проблемой должен за полминуты понять, работают ли здесь с его
вопросом, и отправить документы на оценку.

Отсюда два следствия в устройстве сайта.

**Стоимость определяется индивидуально.** Дела с одинаковым названием
отличаются по объёму в разы, поэтому опубликованы минимальные цены со словом
«от», а точная сумма согласуется после изучения документов. Автоматической
корзины и оплаты «в один клик» нет намеренно.

**Главное действие — отправить обращение с документами.** Форма принимает
описание ситуации и вложения, заявка мгновенно уходит юристу в Telegram
вместе с файлами, и он связывается с клиентом напрямую.

## Что на сайте

**Содержательные разделы.** Главная, «О компании», шесть направлений практики
(семейные и имущественные дела, наследство, земля и недвижимость,
административные дела, права военнослужащих, апелляция и кассация), отдельный
раздел для бизнеса, контакты.

**Стоимость и оплата.** Цены по форматам работы, порядок оплаты банковской
картой, правила оплаты и безопасности платежей, порядок возврата средств
и отказа от услуг, реквизиты. Состав этих страниц продиктован требованиями
Банка ВТБ к интернет-магазину — они условие подключения интернет-эквайринга.

**Правовые документы.** Политика обработки персональных данных, согласие
на обработку, политика cookies. Баннер согласия управляет загрузкой аналитики.

**Приём обращений.** Форма с валидацией на сервере, защитой от ботов,
ограничением частоты и проверкой вложений по сигнатуре файла, а не по
расширению. Готовая карточка заявки приходит в Telegram: контакты клиента,
описание ситуации, кнопки для связи и следом сами документы.

**Поисковая оптимизация.** Уникальные метаданные каждой страницы, карта сайта,
разметка Schema.org, OpenGraph. Аналитика — Яндекс.Метрика, подключается
только после согласия посетителя на cookie.

## Устройство

Next.js 16 (App Router), TypeScript, Tailwind CSS v4, Zod для валидации.

**Базы данных нет, и она не нужна.** Содержание страниц — типизированные
модули в `src/content`, страницы собираются статически. Обращения не хранятся
на сервере: они уходят в Telegram и живут в переписке. Вложения обрабатываются
в памяти и на диск не пишутся.

Единственное состояние, которое переживает перезапуск, — сертификаты Caddy.
Это делает сервер полностью заменяемым: потерять нечего.

```
src/
├── app/           маршруты, карта сайта, robots, обработчик формы
├── components/    layout, ui, блоки страниц, формы, аналитика
├── content/       практики, тексты, контакты, реквизиты, цены, правовые документы
├── lib/           валидация, Telegram, карточка заявки, файлы, ограничение частоты, SEO
└── styles/        дизайн-токены и базовые стили
```

## Развёртывание

### Из чего состоит

Два контейнера, описанных в `compose.yaml`:

- **`app`** — приложение Next.js, слушает порт 3000 внутри сети Docker
  и наружу не выставлен;
- **`caddy`** — принимает трафик на портах 80 и 443.

### Зачем Caddy

Caddy закрывает четыре задачи, каждую из которых иначе пришлось бы решать
отдельно:

1. **Сертификат HTTPS.** Получает и продлевает его в Let's Encrypt
   самостоятельно. Связка nginx с certbot потребовала бы отдельной установки,
   первичного выпуска и заботы о продлении — здесь этого нет вовсе.
2. **Проксирование** запросов на контейнер приложения.
3. **Редирект `www`** на основной домен. Это не косметика: canonical
   на страницах указывает адрес без `www`, и обслуживать сайт на обоих именах
   значило бы создать дубли для поисковиков.
4. **Передача реального IP посетителя** в заголовках. От этого зависит
   ограничение частоты обращений и фиксация IP в следе согласия на обработку
   персональных данных — без проброса всё выглядело бы как запросы с одного
   адреса.

Конфигурация занимает пару десятков строк в `Caddyfile`.

### Образ

**Готового образа нет, он собирается на месте.** В реестрах вроде Docker Hub
ничего не публикуется. Сборку запускает команда развёртывания, читая
`Dockerfile`.

Сборка многоэтапная:

```
deps     устанавливает зависимости по package-lock.json
builder  собирает приложение
runner   финальный образ
```

В итоговый образ не попадают ни исходники, ни инструменты разработки —
только самодостаточная сборка Next.js, статика и `public`. Приложение внутри
работает под непривилегированным пользователем.

Первая сборка занимает несколько минут, последующие быстрее за счёт кеша слоёв.

### Переменные окружения

Значения хранятся в `.env` в корне проекта. В репозиторий он не попадает
и на каждом сервере создаётся заново — за образец берётся `.env.example`.

| Переменная | Назначение |
|---|---|
| `TELEGRAM_BOT_TOKEN` | Токен бота, через который приходят заявки |
| `TELEGRAM_CHAT_ID` | Получатели уведомлений, несколько — через запятую |
| `NEXT_PUBLIC_YANDEX_METRIKA_ID` | Счётчик Метрики; пусто — аналитика не подключается |

Каждый получатель должен сам открыть чат с ботом и нажать «Запустить»:
Telegram запрещает ботам писать первыми, и без этого шага уведомления
не придут даже при верных настройках.

> **Про счётчик Метрики.** Переменные с префиксом `NEXT_PUBLIC_` подставляются
> в код **на этапе сборки**, а не читаются при запуске. Поэтому номер счётчика
> передаётся аргументом сборки, и при его замене нужна пересборка образа —
> простого перезапуска недостаточно.

### Запуск

```bash
cp .env.example .env      # заполнить значения
docker compose up -d --build
```

Первый запуск собирает образ и выпускает сертификат. Порядок действий
с сервером, доменом и DNS — в [docs/deploy.md](./docs/deploy.md).

### Обновление и обслуживание

```bash
git pull
docker compose up -d --build     # пересобрать и перезапустить

docker compose logs -f app       # логи приложения
docker compose logs -f caddy     # выпуск сертификата, ошибки TLS
docker compose restart           # перезапуск без пересборки
docker compose ps                # состояние контейнеров
```

Старый контейнер останавливается только после того, как новый образ собран.

### Смена сервера

Состояния на сервере нет, поэтому переезд сводится к установке Docker,
клонированию репозитория, переносу `.env` и запуску. Сертификат выпишется
заново автоматически, останется переключить A-записи домена.
